Melbourne catchment model · the Optilogic input pipeline

Four builds, in the order they have to run

Raw scan events at one end, a folder you upload to Optilogic at the other. Each step is a script you can run on its own, and the order between them is a real dependency — not a convention. This is all four, end to end, with the arithmetic each one is responsible for.

1The measurementexport_model_factors.py 2The delivery entitysrc/chain2 3The collection entitysrc/chain1 4The combined modelsrc/final

The dependency, which is not the same as the order

Three of the four are genuinely chained. The fourth is not: chain 1 does not read chain 2 — it is extracted from an older build that had both chains together, so it can be run at any point before the merge. It sits third because that is where it is least confusing, not because step 2 produces anything it needs.

Running it

uv run python build_all.py # all four, in order uv run python build_all.py --skip-export # start at chain 2 (no raw scans here) uv run python build_all.py --rebuild # re-read the raw scan CSV in step 1

Each step is also a script on its own, and the package form (python -m src all) runs the same path one module per table. Where the raw scans do not live — a DataStar workspace — step 1 cannot run and the drift guard has nothing to compare against: use --skip-export, and treat the committed inputs/factors_observed/ as the measurement.

1

export_model_factors.py

The measurement

Scans to factors — the only step that reads the raw events, and the only one that filters.

REDUCTION

The reduction — one row per parcel

Six steps, read top to bottom, in the order a parcel experiences them: it is lodged, Melbourne sorts it, a depot delivers it. Each step owns a named set of columns and nothing else, so any column in the output can be traced to the one rule that produced it.

Three evidence bars, deliberately different

Eight scan events can place a parcel in a building, and the script uses three different subsets of them for three different questions. They are not a trust ranking — they differ only on the boundary events, and the rule that decides each cell is what does a false positive cost this particular number?

FACTORS

The factors — and the four dials that cut them

The per-parcel rows become the model's factors here, and this is the only place the filters are applied. That is deliberate: chain 2 consumes whatever it got and cannot quietly re-filter the measurement it is meant to be reproducing.

Why this is a separate step from chain 2

It reads 2.96 M events and takes minutes, where chain 2 takes seconds. Splitting them means the expensive measurement is made once and the cheap model build can be re-run freely — and it is what allows chain 2's drift guard to check the committed CSVs against a live re-derivation from the cache. A stale export fails the model, loudly, rather than quietly shipping.

src/chain2 · build_chain2.py

The delivery entity

Sources, sort and delivery, built entirely from the measured factors.

What goes in, and how much of it is a choice

Three folders, and they are not the same kind of thing. Keeping them apart is the point of the arrangement: you can always answer "is this number measured or did we pick it?" by asking which folder it came from.

Source data

inputs/melbourne/

The day itself, plus the geography. The demand table is the model's magnitude — the same 20 May parcels the scans describe, 14 articles apart.

  • temp_clustered.csv — parcel counts by cluster and product
  • cluster_summary.csv — delivery zone centroids
  • all-data.xlsx — facility coordinates
Observed

inputs/factors_observed/

The measurement, already filtered. export_model_factors.py applies the four filter dials once, here, so chain 2 consumes what it got and cannot re-filter.

  • obs_joint — stage / interstate / Victoria per depot × class
  • obs_demand — the measured delivery magnitude
  • obs_recv_entry, obs_round2, obs_delivery — the stage lanes
Assumed

inputs/factors_assumed/

Hand-managed. Every genuinely chosen number in chain 2 lives in one of these eleven files, which is what makes the assumption count auditable.

  • dials.csv — the switches and thresholds
  • machine_rates, operating_hours, pud_capacity
  • site_sorters, transport_modes, unload_mix, class_hub_split
SETUP

Setup — and the guard that keeps the measurement honest

Config reads the dials, Topology derives the network — which sites sort, which depots deliver, which supplier families exist — and Observed loads the measured factors. Then Observed does something the other two do not: it re-derives those factors from the scan cache and refuses to continue if they disagree.

PREPARE

Prepare — the measured balance

Two pieces of work that belong to no single table, so several tables can read them. load_source_data brings in the day and the coordinates. measure_balance does the arithmetic the whole entity rests on: the floored scan joint applied to the model's own demand, per depot × class, integerised by largest remainder so every row sums exactly to that depot's demand.

stage + interstate + Victoria same-day = D per depot × class, exactly

There is no free parameter in that line — it balances by construction, which is why chain 2 needs no pickup machinery to close. What comes out of it is the three supplier families (SUP_STAGE_*, SUP_INT_*, SUP_VIC_*), the cross-dock lanes split out of the joint, and each depot's throughput cap.

TABLES

Tables — twenty modules, and the order is load-bearing

One module per CSV, named for the CSV it writes, so ls src/chain2/tables/ and ls of the output folder match. They run in ORDER, and that order is not alphabetical — a table is rarely computable from the inputs alone, so each module leaves what a later one needs on the shared Chain2Model object.

CHECKS · OUTPUT

Checks, then the folder

The checks read the written CSVs back off disk — not the in-memory frames — and assert them against the measurement. Supplier caps must equal the measured stage and Victoria totals to the article; every depot's OriginMix stage share must match its measurement within half a point; and a stage-4 check compares where the model despatches from against where the scans do. Then summarise lists what was written and sweeps out retired tables, so a file from an older build cannot ride along in the upload.

Two ways to run the same path

The pipeline exists twice over. build_chain2.py is the flat, notebook-derived script that build_all.py runs; src/chain2/ is the same build as a package, one module per table, driven by python -m src chain2. Both read the same three folders and write the same twenty CSVs to the same place.

python -m src all --skip-export # chain2 → chain1 → final

Step 0 is deliberately outside chain 2. It reads 2.96 M scan events and takes minutes where chain 2 takes seconds, and the four filter dials are applied there, once — so chain 2 consumes whatever it got and cannot quietly re-filter the measurement it is supposed to be reproducing.

src/chain1 · build_chain1.py

The collection entity

Pickup, round-0 sort and the two sinks — cut out of an older build, not re-derived.

The extraction

Chain 1 has no Config and reads no dials, because there is nothing here to steer. Even the list of origin clusters is read off the source build's own suppliers rather than hardcoded — so if that build is regenerated under different rules, chain 1 follows it instead of drifting away from it.

The order, and what it encodes

Seventeen modules, one per table, each holding a single selection rule. Four of them exist before the others because their output is the test the others run.

The balance, and what it is not

Everything collected either leaves the state after one hub sort, or is kept on site for tomorrow. There is no third destination — nothing lodged in Melbourne is delivered in Melbourne today, and that is structural in the recipe table rather than enforced by the check.

P 46,199 = OUT 41,857 (CZ_Interstate_*) + L 4,342 (CZ_LocalTerm_*)

The assert is an arithmetic check that the extraction did not lose a family. If the source build's pickup rules move, the sum stops closing and the build fails rather than shipping a broken entity.

Open here, and only here

LOCAL_KEEP_BY_PUD sets the Sort0 terminate, and the pickup despatch split stays pinned to its pre-Change-26 values — because the scan extract is delivery-side and says nothing about despatch. The lodgement-side extract, the same query selected on lodgement facility, is what would turn these assumptions into measurements. Chain 2's measured Victoria same-day volume is the nearest evidence available in the meantime.

src/final · build_final.py

The combined model

Both entities read back off disk and merged into the folder you upload.

The combine

It reads from disk rather than taking the two models in memory, and that is what makes the run order a real dependency: chain 2 and chain 1 must both have been built before this runs.

The one real merge

Everywhere else the entities are kept apart. Here they cannot be: the same machine at a shared site serves both chains, and each entity sized it for its own touches only — chain 1 for the pickup it despatches, chain 2 for the arrivals it sorts.

Two ledgers, not one identity

There is no combined balance to check, and that is a finding rather than an omission. Collection and delivery are independent daily activities, so the model carries two ledgers:

chain 1 (assumed) P 46,199 = OUT 41,857 + L 4,342 chain 2 (measured) D 167,431 = stage 37,002 + VIC 77,939 + interstate 52,490

What the measurement does offer the assumption is an inference: the 77,939 EA lodged in Victoria and delivered the same day is delivery-side evidence about the size of the collection activity chain 1 models with an assumed P of 46,199. That is the number to revisit PICKUP_TOTAL with when the lodgement-side extract lands.

The one thing that is not independent

The base. If the two entities count different days, any figure that adds a chain-1 number to a chain-2 number is mixing bases — so the build prints the scale factor rather than letting the mixing pass unremarked. On the last build both sat on the zone table's 167,431 EA and the factor was 1.0000. Chain 2's rebuild on the 18 August rules moves it to 166,849 EA, so expect a scale of 0.9965 until the chain-1 source build is rebased too.
