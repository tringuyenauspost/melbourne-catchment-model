01

What we were doing before

  • The mix was never stated anywhere. Three separate mechanisms decided it, and none of them was a percentage anyone had signed off.
  • Which machines a parcel was allowed to use was hard-coded in the notebook — interstate freight could only go ULD or long reach, Victorian freight only ULD or hand. A real operational claim, buried in an if statement.
  • The interstate 60/40 was enforced by cloning the product. We split the arrival into ..._ULD_Pickup and ..._LR_Pickup, gave each 60% and 40% of supply, and gave each exactly one recipe. Exact — but it took two products to express one ratio, and only worked at the point of arrival.
  • Everywhere else, cost decided. ULD is $0.015/EA, long reach $0.020, hand $0.050. The cheapest machine filled first, so the mix we reported was a by-product of how we had sized the docks.
  • The consequence: hand unload came out at exactly zero. The most expensive activity per parcel, and the model booked none of it.
  • We knew this and had documented it as unfixable. The notebook carried a bounded setting that deliberately refused to run, with a note explaining that a work-centre capacity limit bounds the whole machine — and a hub's ULD dock is shared with collection and second-sort volume, so there was no way to bound just the interstate slice.
02

What Optilogic suggested

  • Two tables we were not using: UserDefinedVariables and UserDefinedConstraints, demonstrated in their AusPost — Sort ByPass v2 model.
  • A "variable" is really an expression. Each row is one term: a filter over quantities the model already produces, plus a coefficient. Rows sharing a name add together.
  • Their worked example — long reach forced to half of all unloading at a hub:
    • term 1: total unloading across both methods, coefficient −0.5
    • term 2: long-reach unloading only, coefficient +1
    • constraint: the sum is fixed at 0 → long reach = 50% of the total
  • The percentage lives in the coefficient, not in the constraint value — so the ratio holds against a total the solver is free to change.
  • Their framing: percentages become scenario items or pre-calculated columns, so testing a different mix is a switch rather than a rebuild.
03

How we implemented it

  • The insight that unlocked it: a user-defined variable filters by product and process at the same time. A work-centre capacity limit cannot. That is exactly what lets us bound the interstate share of a dock that also handles collection and second-sort volume — so the setting we had written off as impossible became buildable.
  • The shares now live in a file anyone can read — inputs/factors_assumed/unload_mix.csv — one row per family per method, marked as placeholders until Operations confirm them.
  • We set a band, not a fixed number. A hard equality goes infeasible the moment a machine runs short; a band lets the mix flex and shows us which way it wants to move. Each band is two constraints — a floor and a ceiling.
  • We never constrain every method. Two methods that must add to 100%, plus the model's own flow balance, is one equation too many — any rounding makes it unsolvable with no useful error. One method per family is always left as the remainder.
  • The cloned products are gone. Four interstate arrival products collapse back to two, and the 60/40 moves out of the supply table into the constraint. This is the "hard-coded product split" we were asked to remove.
  • Off by default. With the switch off the model rebuilds byte-for-byte identical to before — verified by a full on-and-off round trip — so nothing changes until someone deliberately turns it on.
Two mistakes found on the way — worth knowing, because both were silent
  • The first upload looked like it worked and did nothing. We had named each constraint after the variable it bounds. Cosmic Frog keeps both names in one namespace, so all 26 constraints were dropped during pre-processing. The variables still calculated, the solve returned clean — and the mix was completely unbounded. Optilogic's NEO assistant found it in the validation report. Fixed by prefixing the names, plus a check in our build that now fails loudly if it ever recurs.
  • Our own capacity check was measuring the wrong thing — the sorting workload rather than the unloading workload, which differ wherever freight is cross-docked. It understated Melbourne Parcel by 44%. Corrected, and the figures now reconcile exactly to the solve.

05

What to decide next

  • The numbers in the file are placeholders and Operations need to confirm them. Interstate 60/40 matches what we already assumed. Victoria 85/15 is invented — there is no measurement behind it, and it is the reason hand unload is no longer zero. This is the single most useful question to take to the business.
  • The ceiling is doing all the work, not the target. ULD is the cheapest machine, so the solver goes to the top of every band: we asked for 60% interstate and got 65%, asked for 85% Victoria and got 90%. That is correct behaviour, but it means the number in the file is not the number in the answer. If we want the target hit exactly, we set the band to zero and pin it.
  • Collection is still unbounded — 41,857 EA/day at 100% ULD. Extending the same mechanism to chain 1 is straightforward but sits behind a rebuild we already owe.
  • Same pattern, other questions. Loading is symmetric to unloading and would be a data change, not a code change. The sort machines are the more interesting target — that is where the deep-sort work lands.
